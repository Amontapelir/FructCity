# Как здесь работают

Короткий свод правил про ветки, задачи и вливание. Про устройство слоёв
и причины решений — `backend/README.md` и docstring самих модулей: они
пишутся так, чтобы отвечать на «почему», а не только на «что».

## Ветки

`main` держим рабочей: каждый коммит в ней — состояние, на котором тесты
зелёные. Всё остальное делается в отдельной ветке и попадает в `main`
через pull request.

Имя ветки — из типа и сути, латиницей:

```
git switch -c feat/holidays-in-slots     # новая возможность
git switch -c fix/order-total-negative   # исправление дефекта
git switch -c chore/alembic-baseline     # обвязка, документация, зависимости
```

Почему не работать прямо в `main`: пока ветка отдельная, любую неудачную
попытку можно выбросить целиком (`git switch main && git branch -D ...`)
и ничего не объяснять истории. В `main` каждая ошибка остаётся навсегда —
её можно только отменить новым коммитом.

## Задачи

Задачи живут в issues. Крупные заводятся по мере того, как берутся в
работу, мелкие — сразу.

Обязательное поле в шаблоне задачи — **«чем проверяется»**. «Сделано» в
этом проекте значит «есть тест, который краснеет без изменения», а не
«работает у меня». Если это поле не заполняется — задача сформулирована
недостаточно, и её стоит сначала додумать.

В коммите и в PR ставится `Закрывает #12` — тогда issue закроется само
при вливании, и история будет отвечать на вопрос «зачем это меняли».

## Коммиты

Один коммит — один законченный шаг. Хороший ориентир: **зелёные тесты —
повод для коммита.** Тогда любая точка в истории заведомо рабочая, и
откатываться есть куда.

Сообщение — по-русски, повелительным наклонением, без точки:

```
Добавить праздничные дни в расчёт слотов
Исправить порядок прав в /api/admin/me
```

Если нужно объяснить «почему» — второй абзац после пустой строки. Это то
место, где через полгода найдётся ответ на вопрос «зачем так странно».

## Pull request

Шаблон открывается сам и содержит список проверок. Два пункта в нём не
формальность:

- **тест проверен подменой** — ломаешь исправление, тест обязан упасть.
  Тест, который зелёный в обоих случаях, не проверяет ничего;
- **схема базы** — если менялась, нужна ревизия alembic. Два способа
  менять схему (модели и миграции по отдельности) означают два
  расходящихся представления о ней.

Автоматический прогон (`.github/workflows/tests.yml`) гоняет набор на
Linux и настоящем PostgreSQL — там выполняются проверки, которые на
Windows пропускаются: символические ссылки и гонка на последнем товаре.
Красный прогон не вливаем.

## Чего не делать

- Не коммитить `.env` и содержимое `data/` — там пароли и персональные
  данные покупателей. Попав в историю, они остаются в ней навсегда:
  удаление файла старые снимки не трогает. За этим следит отдельная
  работа в CI.
- Не делать `git push --force` в `main`.
- Не использовать `git reset --hard`, пока есть несохранённые изменения:
  это единственная команда здесь, которая не прощает ошибок.
